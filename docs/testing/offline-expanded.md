## 2. 每类测试做了什么、验证了什么、结果如何

### 2.1 基线回归测试（198 项通过）

**做了什么**：运行仓库原有的全部测试，包括命令行、ST 前端、Python/C++ 后端、运行时块、往返测试等。

**验证能力**：plcforge 在已覆盖的通用 ST/SCL、PLCopen XML、Python 后端、C++ 后端、运行时块等场景下没有回归。

**结果**：全部通过。

**说明什么**：本次扩展没有破坏已有功能。但这些测试的语料是项目自制示例或通用场景，不是四家厂商的真实工程导出。

### 2.2 独立预期逻辑测试（`tests/test_expected_logic.py`）

**做了什么**：不依赖任何生成结果，用手算或独立公式写出预期，再检查 plcforge 转换后的行为。

**覆盖内容**：

| 测试组 | 验证能力 | 结果 |
|---|---|---|
| 标识符映射 | PLC 标识符（如 `%IX0.0`、`Motor Start`、`9volts`）转成 Python/C++ 后叫什么；Python/C++ 关键字冲突如何处理；重名时如何编号 | 通过 |
| 手写 Python 提升后再生成 | 把手工写的 Python 代码提升为 ST，再解析回 Python/C++，检查水箱定时、边沿触发、整数除余、限幅、循环、枚举、结构体 | 大部分通过；`convert(value, "DINT")` 一项失败（OFFLINE-001） |
| REAL 量级 | 大、小、负 REAL 数的转换与计算结果 | 通过 |

**结果**：20 项新增测试中，19 项通过，1 项标记为严格预期失败（xfail）。

**说明什么**：在命名、基础数值、结构体、枚举、循环、定时器、边沿触发等场景，转换结果与手算预期一致；但 `convert(..., "DINT")` 这条路径目前会生成无法运行的名称 `TO_DINT`。

### 2.3 Python/C++ 交叉对拍与往返测试（`tests/test_offline_differential.py`）

**做了什么**：同一份 ST 源文件，分别走两条路径转换，再逐扫描比较结果：

- **直接路径**：ST → Python，ST → C++
- **往返路径**：ST → Python → 再提升为 ST → 再生成 Python/C++

预期值全部用独立公式计算，不用生成代码的结果互相套用。

#### 2.3.1 数值矩阵

**验证能力**：整数除法、取余、限幅、WORD 位与、负步长循环、REAL 算式在两个后端和往返后是否一致。

**输入**：4 个边界值 + 固定种子 20261029 生成的 512 行随机输入，共 516 行。

**结果**：直接路径与往返路径均通过；整数精确相等，REAL 相对/绝对容差 1e-6。

**说明什么**：在大量边界和随机输入下，Python 后端、C++ 后端、往返后的 Python 后端在数值语义上保持一致，符合 IEC 61131 的向零截断除法和包含端点的循环语义。

#### 2.3.2 双实例时序

**验证能力**：两个 TON/R_TRIG 实例在不同输入、复位、时间推进下，状态是否互相隔离；TON 的 1500ms 边界是否正确；R_TRIG 是否只脉冲一个扫描周期。

**输入**：9 个绝对时间点，两个实例输入不同。

**结果**：直接路径与往返路径均通过；TIME 容差 1e-9。

**说明什么**：定时器和边沿触发块的实例隔离、复位优先级、边界条件在 Python 和 C++ 后端均正确。

#### 2.3.3 两个 C++ 最小缺陷复现

| 测试 | 验证能力 | 结果 |
|---|---|---|
| 前向 FB 依赖 | PROGRAM 先使用、FB 后定义时，C++ 能否编译 | 失败（OFFLINE-002） |
| 函数往返后严格编译 | 普通函数经 Python→ST 往返后，C++ 是否在 `-Werror` 下无警告编译 | 失败（OFFLINE-003） |

**说明什么**：这两个失败不代表数值算错，而是生成代码的 C++ 编译问题。详见第 4 节。

### 2.4 合成工程与长扫描测试（`tests/test_offline_synthetic.py`）

**做了什么**：用程序自动生成跨多个源文件、含函数调用链和大量 FB 实例/数组的工程，验证解析、链接、Python 生成、C++ 编译执行、往返行为是否一致。

#### 2.4.1 三档合成工程

| 档位 | 源文件数 / POU 数 | 每个 Factory 的 FB 实例 | 每个数组长度 / 总元素 | 调用链深度 | 扫描数 | 结果 |
|---|---:|---:|---:|---:|---:|:---|
| 小 | 13 | 8 | 8 / 64 | 4 | 20 | 通过 |
| 中 | 81 | 64 | 32 / 2048 | 16 | 40 | 通过 |
| 大 | 289 | 256 | 128 / 32768 | 32 | 64 | 通过 |

**验证能力**：

- 跨文件解析与链接能否处理依赖顺序输入
- 大量 FB 实例和数组元素下，Python 直接生成、Python 往返生成、C++ 直接编译执行是否给出一致结果
- 两个 Factory 实例启停模式不同（一个每 3 扫描停一次，一个每 5 扫描启一次），状态是否独立

**结果**：

- Python 直接路径：通过
- Python 往返路径：通过
- C++ 直接编译执行：通过
- 大档使用依赖顺序输入；逆依赖顺序和函数往返后的 C++ 严格编译未通过，单独保留为缺陷复现，没有通过调整输入顺序或关闭告警来绕过

**说明什么**：在受控的大规模合成工程里，当前 plcforge 能把依赖顺序正确的多文件工程正确解析、生成 Python 和 C++，并逐扫描核对两个独立实例的状态。但这只证明“生成和运行正确”，不能证明任何真实厂商工程的兼容性。

#### 2.4.2 10 万扫描长扫描

**做了什么**：Python 直接路径和往返路径各执行 100000 次扫描，模拟 1000 秒（先 `run_cycles(40000)`，再 `run_for(600.0)`）；C++ 直接路径也执行 100000 次扫描。

**验证能力**：

- 扫描引擎分段推进（cycles + for duration）是否正确
- 长时间运行下累计值、模拟时钟、输入输出回调是否按公式增长
- 未运行的另一个实例是否不受影响

**结果**：通过。

**说明什么**：在当前本机环境下，ScanEngine 能稳定推进 10 万次扫描并保持一致状态。**这是模拟时间验证，不是实时性能或整夜墙钟浸泡测试。**

### 2.5 注错验证（`scripts/verify_offline_mutations.py`）

**做了什么**：在临时副本中修改一次产品源码，运行三项新增测试，看断言是否能抓住错误；未变异的对照必须全部通过。

| 注错位置 | 修改内容 | 被抓住的表现 |
|---|---|---|
| 整数除法 | 向零截断改成 Python floor | 首行 quotient/remainder 从 (-2,-1) 变成 (-3,3) |
| FOR 循环 | 去掉端点补偿 | 5+3+1 的 9 变成 8 |
| TON 边界 | `ET >= PT` 改成 `ET > PT` | PT 边界 ready 仍为 False |
| 名称冲突编号 | 重名编号从 2 改成 3 | `motor_2` 变成 `motor_3` |

**结果**：对照 3 项通过；4/4 注错均被断言抓住。

**说明什么**：这几条核心逻辑路径的测试对常见实现错误敏感。但这只是 4 个定向抽查，不是穷举变异测试，不能证明所有潜在错误都会被发现。

## 3. 已确认但未修复的三处产品缺陷

详细源码、阶段定位、最小复现命令见 [defect-reproductions.md](defect-reproductions.md)。

| 编号 | 触发场景 | 实际结果 | 影响说明 | 当前状态 |
|---|---|---|---|---|
| **OFFLINE-001** | 手写 Python 里用 `convert(value, "DINT")` | 提升为 ST 时生成 `TO_DINT(value)`；再转回 Python 执行时报 `NameError: name 'TO_DINT' is not defined` | 任何依赖 Python→ST→Python 的类型转换都会失败；用户无法通过 lift 再转换的方式使用 `convert` | 严格 xfail，未修复 |
| **OFFLINE-002** | ST 源中 PROGRAM 先使用某个 FB，FB 定义写在后面 | Python 后端正常，但生成 C++ 时因为 `Cell` 类型还没定义就使用，编译失败 `unknown type name 'Cell'` | 多文件工程或单文件中定义顺序不符合“先定义后使用”时，C++ 输出无法编译；需要手动调整源文件顺序或等待 emitter 排序 | 严格 xfail，未修复 |
| **OFFLINE-003** | 普通 FUNCTION 经 Python→ST 往返后再生成 C++ | 函数体多出 `_result = _result;`，在 `-Wall -Wextra -Werror` 下编译报错 | 函数往返后的 C++ 严格编译失败；虽然数值结果可能正确，但无法通过无警告编译 | 严格 xfail，未修复 |

**为什么标记为 xfail**：这三个用例使用 pytest 的 `strict=True` xfail。现在它们失败是“符合预期”的；未来如果产品修复了，它们会变成 XPASS(strict)，测试套件会强制提醒移除 xfail 标记。这样既保留了三处缺陷的可见性，又不会让整轮全量测试因为一个已知失败而中断。

## 4. 四家厂商兼容性结论（整理自 #1 报告）

本任务没有重新调查厂商格式，只整理 #1 任务已提交报告 `docs/testing/vendor-compatibility.md` 的证据。结论口径如下：

| 结论等级 | 含义 |
|---|---|
| 工程可打开 | 能识别原生工程/归档格式并建立正确语义模型 |
| 程序可提取 | 能提取 POU、变量、类型、程序体，并记录缺失 |
| 代码可转换 | 能经现有流水线完成 `check` 和目标代码生成 |
| 行为已验证 | 生成代码已运行，且预期序列可追溯至厂商软件/控制器 |

### 4.1 分厂商结论

| 厂商 | 原生工程/归档 | 通用 SCL/ST 或 PLCopen XML 路径 | 本次真实样本实测 |
|---|---|---|---|
| **西门子** | 不支持（`.ap21`/`.zap21` 无入口；SimaticML 不是 PLCopen XML） | `.scl` 文本是候选入口，但未用真实 TIA 导出实测 | V19 SimaticML 样本：`well-formed`，但 0 POU，`PF002`，退出 1 |
| **欧姆龙** | 不支持（`.smc2`/`.csm2` 无入口） | IEC 61131-10 XML 导入官方确认，但无真实导出样本；`.st` 复制正文候选 | 未验证 |
| **汇川** | 不支持（AutoShop `.hcp`/`.hclib`、InoProShop `.project` 无入口） | InoProShop PLCopen XML 是候选入口 | 标称 V1.9.1.6 样本：9 个 ST POU 可提取并生成 Python，37 个警告；439 个扩展全局变量和 2 个任务丢失；行为未验证 |
| **施耐德** | 不支持（Machine Expert `.project`、Control Expert `.STU`/`.STA` 无入口） | Machine Expert PLCopen XML 是候选入口；XEF 是另一种 XML | V15.0 XEF 样本：`well-formed`，默认 `PF001`+`PF002`，强制 PLCopen 也为 `PF002`，退出 1 |

### 4.2 关键边界

- **当前 plcforge 没有四家厂商原生工程或归档的专用读取入口**。`.xml` 后缀、ZIP 可解压、文本可查看都不等于“工程可打开”。
- **现有可行入口只有通用 SCL/ST 和 PLCopen XML**。西门子 SimaticML、施耐德 Control Expert XEF 必须单独适配。
- **四家厂商的行为均未验证**。汇川样本只做到了“部分 POU 可提取并生成 Python”，全局变量、任务、运动控制依赖都丢失了；西门子 SimaticML 和施耐德 XEF 当前直接失败；欧姆龙缺少真实样本。

## 5. 这些结果能证明什么、不能证明什么

### 5.1 能证明的

1. **通用逻辑转换在已覆盖子集内是正确的**：整数除法、取余、循环、枚举、结构体、数组、定时器、边沿触发、双实例隔离等，在 Python 后端、C++ 后端、往返路径下均与独立预期一致。
2. **大规模合成工程在当前受控条件下可生成、编译、运行**：289 个 POU、256 个 FB 实例、32768 个数组元素、32 级调用链、64 次扫描的核对通过；10 万次扫描的模拟时间推进通过。
3. **核心断言对常见错误敏感**：4 类定向注错均被测试抓住。
4. **基线没有回归**：原有 198 项测试全部通过，`ruff`/`mypy` 通过。

### 5.2 不能证明的

1. **不能证明四家厂商工程兼容**：厂商原生工程、归档、SimaticML、XEF 等均未支持；汇川 PLCopen XML 样本只做了部分转换且行为未验证。
2. **不能证明实时性能或工业规模承载**：10 万扫描是模拟时间，不是实时墙钟测试；计时只作本机观测，没有性能门槛。
3. **不能证明所有边界条件**：测试是设计出来的场景，不是穷举；未覆盖所有溢出策略、字符串、浮点异常、并发 IO、硬件中断等。
4. **不能证明三处缺陷只在当前用例出现**：OFFLINE-001/002/003 是已发现的最小复现，同类模式可能在其他输入中触发。
5. **不能把覆盖率等同于正确率**：全量覆盖率从 80% 提升到 82%，但覆盖到的代码也可能包含缺陷复现路径，覆盖率高不等于没有 bug。
